# presidio-ru-core — ядро маскирования для LiteLLM

Этот форк обслуживает один русский профиль. Порт передаёт текстовый блок и ожидает упорядоченные диапазоны символов для замены. Блоки могут содержать русский текст, исходный код и секреты. Политика исключений, перекрытия диапазонов и контекст влияют на результат. Восстановление исходных значений выполняет LiteLLM в пределах одного запроса.

## Что вошло в первую сборку

Основа репозитория — тег Presidio `2.2.366`. Пакет анализатора восстановлен из wheel работающего RU-профиля `2.2.366-1`, SHA-256 `420d7512625401e1a8750a846dd350d2e9887c261f85c153e661adeee034df83`. Номер сборки форка — `2.2.366+ru.mask1`.

- Правило email находит очередной обязательный символ `@` и выделяет участок до ближайших пробела, табуляции или перевода строки с обеих сторон. Штатное регулярное выражение работает на оригинальном буфере и возвращает исходные координаты. Несколько адресов в одном участке проверяются вместе. Бюджет времени общий для всех участков. Пользовательские выражения и нестандартные флаги проходят полную проверку.
- При запуске словарь форм имён компилируется в выражение с общими префиксами. В одной ветке более длинная форма проверяется первой.
- Gitleaks строит индекс строк после первого кандидата, использует двоичный поиск для координат и создаёт таблицу позиций UTF-8 после первой принятой находки в тексте с не-ASCII-символами.

## Использование mask3

Для маскирования оберните вызов анализатора в `strict_scan()`. Таймаут встроенного регулярного выражения, проверки IBAN или регулярного выражения списка исключений прерывает вызов и поднимает `IncompleteScan`. Сервис может повторить операцию или отклонить весь запрос. Область действия ограничена текущим контекстом исполнения. Обычный вызов SDK сохраняет прежнюю обработку таймаутов.

```python
from presidio_analyzer import strict_scan

with strict_scan():
    findings = engine.analyze(text=text, language="ru")
```

Встроенный Gitleaks при наличии `pyahocorasick` индексирует ключевые слова TOML при загрузке правил. Правила без обязательного слова проверяются на каждом тексте. Отобранные правила выполняются в исходном порядке. В установках с одним RE2 работает прежний поиск по ключевым словам. Внешний RU-профиль может применять собственный индекс.

## Продолжение исследования: 24.11.2026

Следующий этап начат и проверяется исполняемыми тестами. Подробные источники, результаты и нерешённые вопросы собраны в [исследовании](presidio-analyzer/benchmarks/scaling-research.md).

В рабочем дереве после mask3:

- Поиск токена контекста использует двоичный поиск вместо прохода от начала текста для каждой находки. Сохраняются выбор следующего токена в пробеле, Unicode-координаты и ошибка за концом текста. В диагностике этого пути больше нет самого найденного значения и списка слов исходного текста.
- Если все recognizer-level context hooks штатные и ничего не меняют, результаты группируются один раз. При пользовательском hook сохраняется прежний путь, включая доступ к результатам других распознавателей и последовательность изменений metadata.
- `RuCardExpiryRecognizer` принимает `YYYY-MM` только после `card_expiry` или «срок действия карты». Общие даты, полные даты с днём и месяцы 00/13 не принимаются. Это намеренное расширение распознавания, а не оптимизация без изменения результата.
- Исправлены устаревшие тесты конфигурации composite enhancer и проверка benchmark на отсутствующее приватное поле распознавателя.

Задержка, полнота маскирования и ложные срабатывания проверяются раздельно. В `evaluate_ru_port.py` полное покрытие метки отличается от точного совпадения диапазона. Частично закрытая строка подключения не автоматически означает открытый пароль; этот случай требует проверки поддиапазона учётных данных. На отрицательных примерах считается доля затронутых сообщений и явно размеченных безопасных диапазонов. В отчёт не записываются исходные значения.

## Что уже есть в порте

Порт уже содержит отложенный NLP, общий prefilter, локальный/shared/Redis кеш диапазонов, процессы анализатора, ограниченные очереди и карту восстановления в пределах запроса. Дублировать эти механизмы в ядре не требуется. Встроенный Gitleaks и полный профиль измеряются отдельно. Анализатор SDK выдаёт результаты в порядке score и допускает перекрытия разных типов; именно `Detector.detect()` сортирует и объединяет диапазоны для LiteLLM.

## Проверка и воспроизведение

Из корня этого репозитория, используя Python с зависимостями соседнего порта:

```sh
../litellm-presidio-port/.presidio-venv/bin/python \
  presidio-analyzer/benchmarks/compare_ru_port.py \
  presidio-analyzer/dist/presidio_analyzer-2.2.366+ru.mask3-py3-none-any.whl \
  presidio-analyzer --repeats 3 \
  --expected-changes presidio-analyzer/benchmarks/reviewed-span-changes.json

../litellm-presidio-port/.presidio-venv/bin/python \
  presidio-analyzer/benchmarks/evaluate_ru_port.py \
  --output /tmp/ru-quality-and-workers.json

../litellm-presidio-port/.presidio-venv/bin/python \
  presidio-analyzer/benchmarks/evaluate_ru_port.py --workload server --repeats 2 \
  --output /tmp/ru-server-workers.json
```

Сравнение отклоняет любое изменение диапазонов, кроме явно зафиксированной пары старого/нового результата в `reviewed-span-changes.json`. Для текущей правки разрешён только один добавленный диапазон срока карты. Повторы чередуют порядок двух изолированных процессов.

Проверка процессов выполняет одинаковый конечный пакет на 1, 2, 5 и 10 локальных воркерах. Она измеряет CPU, время сканирования, ожидание в пакете и совпадение результатов с последовательным вызовом. Это не тест 10 серверных реплик и не сквозной RPS чата. HTTP, Redis, модель и восстановление ответа в эти числа не входят. Отдельные тесты порта проверяют протокол, batch, кеши, admission и streaming.

## Что остаётся для серверной приёмки

Нужны отдельные прогоны с заданной скоростью поступления запросов на независимых репликах: новые блоки, повтор истории и смесь длинных/коротких запросов. Считать успешные корректные запросы, суммарный CPU, RSS, cache hits, p95/p99 очереди, отказы и обращения к mock-модели. При неполном сканировании обращений к модели быть не должно. Затем повторить с настоящим backend. Очереди делить по стоимости только если измерено вытеснение коротких запросов длинными.

Поиск кандидатов с ограничением окна остаётся отдельным экспериментом. Для каждого правила нужно доказать обязательность маркера и достаточность контекста. Неизвестные флаги, пользовательские выражения и правила без доказательства должны сохранять полный проход. Автоматическое понижение порогов или ослабление checksum ради прохождения датасета недопустимо.

## Сборка

Из `presidio-analyzer/` выполнить `uv build --wheel`. Публикация новой версии и переключение `profile/runtime.lock.txt` не выполнены: существующий mask3 wheel сохранён как baseline. Перед выпуском назначить новую версию, собрать wheel, повторить сравнение именно wheel и перезапустить воркеры с новым ключом кеша профиля.

### Отложенные импорты NLP (исходники, ещё не отдельный wheel)

RU-профиль может импортировать базовые интерфейсы без загрузки spaCy. Классы
Spacy/Stanza/Transformers/Slim доступны по прежним именам и загружаются при
обращении. NoOp сохраняет настоящие spaCy Doc. Две аннотации NlpArtifacts
(`entities`, `tokens`) теперь строковые; `typing.get_type_hints` разрешает
настоящие типы. Побочные эффекты импорта необязательных движков отложены до
обращения к ним. Зависимости не удалены.

Проверка совместимости без скачивания моделей:
`python benchmarks/check_lazy_import_sdk.py` из `presidio-analyzer/` с его
каталогом в PYTHONPATH. Регрессионный запуск в новом процессе находится в
`tests/test_lazy_import_sdk.py`.

Изолированная проверка установленного mask3 плюс только эти изменения:
2 512 диапазонов маскирования и 1 260 контекстов совпали с эталоном;
медиана CPU холодного запуска RU-профиля на Mac снизилась 799 → 479 мс.
Это не измерение пропускной способности чата. Подробности и ограничения:
`../litellm-presidio-port/docs/lazy-import-startup.md` относительно корня
репозитория. Активный wheel порта пока mask3; рабочие изменения других
модулей не входят в этот изолированный результат.
