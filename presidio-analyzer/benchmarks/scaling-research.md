# CPU, качество и масштабирование Presidio RU

Дата исследования: 24.11.2026. Область: ядро `presidio-ru-core` и совместимость с соседним `litellm-presidio-port`. Код порта изучен без изменений. Внешние первичные источники проверены на дату исследования; документация upstream не заменяет проверку зафиксированной версии LiteLLM 1.108.1.

## Вывод

Следующая оптимизация должна уменьшать CPU полного RU-профиля на новых блоках, сохраняя точные диапазоны, оценки и обработку неполной проверки. Порт уже содержит кеширование и ограничение параллелизма. Ускорение одного Gitleaks не доказывает ускорение полного профиля, а добавление реплик само по себе не гарантирует линейный рост успешных запросов чата.

## Что установлено локально

Источники ниже указаны относительно общего рабочего каталога.

| Наблюдение | Проверенный источник | Значение для изменений ядра |
| --- | --- | --- |
| `Detector.detect()` вызывает `engine.analyze()` внутри `strict_scan()` | `litellm-presidio-port/profile/src/detector.py`, метод `detect` | Исключение неполной проверки должно доходить до вызывающего сервиса; частичный результат нельзя считать полным |
| API анализатора отвечает ошибкой при исключении; guardrail отклоняет неверный HTTP-статус, Content-Type, JSON и диапазоны | `src/presidio_ru_litellm/analyzer.py:Handler.do_POST`, `guardrail.py:analyze_text` в порте | Для проверенного одиночного пути предусмотрен отказ до модели; это вывод из исходников, не проведённый здесь аварийный e2e-тест |
| Воркеры — отдельные процессы; каждый загружает свой Detector после fork | `analyzer.py:serve_worker` и запуск процессов | Измерять совокупный CPU и RSS всех процессов; async-параллелизм HTTP не равен параллельному исполнению одного анализатора |
| Есть кеш на 1024 записи на worker и альтернативный shared-memory/Redis слой | `analyzer.py:CachedTextDetector`, `span_cache.py`, `redis_cache.py` | Хранятся keyed digest и диапазоны, включая пустой результат; более 32 диапазонов не кешируются. Ошибка Redis вызывает локальное распознавание, а не разрешение непроверенного текста |
| Ключ кеша зависит от версии Python, lock, файлов профиля, конфигурации и wheel | `span_cache.py:profile_key` | Для измерений обновления нужны новый wheel и новые процессы; кеши старого и нового профиля должны быть разделены |
| Есть общий предел активных проверок, ограниченная очередь и предел блоков одной истории | `guardrail.py:_ScanAdmission`, `PresidioRUGuardrail` | При нескольких экземплярах прокси лимиты суммируются. Увеличение числа прокси может перегрузить общий анализатор |

| Lock профиля ссылается на `2.2.366+ru.mask3`; README порта ещё упоминает mask2 | `profile/runtime.lock.txt`, `README.md` | Фактическую сборку проверять по загруженному пакету/артефакту, а не одному README |

Это описание просмотренного дерева, не утверждение о версии уже работающего сервиса.

## Безопасный отбор кандидатов

RE2 ограничивает время сопоставления линейно длиной текста, но авторы прямо не обещают превосходство над другими движками на каждом выражении. Поэтому замена движка целиком требует замера, а не предположения об ускорении. [RE2 README](https://github.com/google/re2)

RE2 не поддерживает lookaround и backreference; его `\w`, `\d` и граница `\b` имеют ASCII-семантику. Переписывание Unicode-правил Python под эти обозначения способно изменить множество находок. [RE2 syntax](https://github.com/google/re2/wiki/Syntax)

Aho–Corasick подходит для поиска множества фиксированных обязательных литералов одним проходом. API возвращает позиции конца совпадений; Unicode/bytes-режим зависит от сборки. Это механизм отбора, а не замена проверок контекста, checksum, entropy и исключений. [Документация pyahocorasick](https://pyahocorasick.readthedocs.io/en/latest/)

Предлагаемый контракт: для каждого правила исходное совпадение обязательно порождает кандидата; ложные кандидаты допустимы, потерянные — нет. Точная проверка остаётся на исходном тексте. Правило без доказанного обязательного маркера, с пользовательскими флагами или нестандартным выражением идёт прежним полным путём. Нормализованный буфер используется только для выбора правил; его индексы нельзя без доказательства переносить в исходный текст. Для окон отдельно доказываются границы и достаточный контекст: простое обрезание может изменить anchors, lookbehind, lookahead и выбор альтернатив.

Встроенный Gitleaks уже строит необязательный индекс ключевых слов, сохраняет порядок правил и использует собственное преобразование `_lower`. Его замена на общий `casefold()` была бы изменением поведения. Дополнительный индекс должен показывать пользу на полном Detector: внешний профиль уже содержит свой prefilter.

## Контракт LiteLLM

Для предотвращения отправки открытого текста нужен путь `pre_call`; `logging_only` меняет логирование, а не запрос к модели. `output_parse_pii` восстанавливает значения в ответе. Эти возможности описаны upstream, однако их наличие не доказывает безопасность каждого маршрута, payload и потока. [Presidio в LiteLLM](https://docs.litellm.ai/docs/proxy/guardrails/pii_masking_v2)

Авторский отчёт в issue #30728 описывает fail-open для mask-only настроек и пробелы обработки Responses/streaming в исследованной им версии. Это историческое свидетельство класса ошибок, а не доказательство дефекта текущего локального порта или последней версии upstream. Проверять следует фактический override и версию. [LiteLLM issue #30728](https://github.com/BerriAI/litellm/issues/30728)

При обновлении ядра проверить цепочку: timeout точного regex → `IncompleteScan` → ошибка API → отказ guardrail → ноль обращений к mock-провайдеру. Повторить для очереди, отмены, HTTP 500, некорректного JSON, невалидных диапазонов и batch. Отдельно проверить Unicode до находки, одинаковые значения в нескольких сообщениях, JSON tool arguments, токены в нескольких SSE-чанках и независимость двух запросов. Эти проверки должны исполняться в окружении зафиксированного LiteLLM; статический просмотр не заменяет их. `/responses` и нативные маршруты провайдеров считать отдельной матрицей совместимости, а не автоматически поддержанными по успешному Chat Completions.

## План измерений

1. Зафиксировать wheel hashes, commit, Python, зависимости, CPU/квоты, workers, профиль, лимиты и corpus hashes. Профилировать прямой Detector на новых блоках с отключёнными внешними кешами, чтобы найти фактическую долю каждого распознавателя и подготовки текста.
2. Для кандидата оптимизации сравнить исходную и новую реализации на полном наборе ПДн, секретов и обычного кода. Сверять тип, начало, конец, score и нужные downstream metadata. Дополнительно сверить с разметкой precision/recall по типам и ложные срабатывания на MB кода. Равенство прежнему результату и качество относительно разметки — разные критерии.
3. Выполнить Unicode/adversarial набор: кириллица, `İ`, `Σ`, `ſ`, `K`, комбинируемые символы, astral codepoints, отсутствие литерала, множество литералов, длинный почти подходящий токен, границы chunk, нестандартные flags и пользовательское выражение. Проверить строгий и совместимый SDK-режимы, а также отсутствие необязательной библиотеки.
4. Повторить перемешанные пары baseline/candidate минимум несколько раз с прогревом. Публиковать CPU ms/MB, CPU ms/block, wall p50/p95/p99, RSS, число кандидатов и доверительный интервал либо разброс повторов. Отдельно показывать cold start. Нельзя выбирать только выигравшие корпуса.
5. С неизменным профилем запросов сравнить 1, 2, 5, 10 реплик: новый текст, повтор истории, смешанные короткие и длинные блоки. Генератор нагрузки должен поддерживать заданную скорость поступления независимо от времени ответа; иначе длинные ответы сами уменьшают нагрузку. Считать offered/accepted/completed/rejected, backlog, queue wait и завершённые корректные chat requests/s.
6. Сначала использовать mock-провайдер, затем реальный backend. При отключённом Redis, холодном кеше и после обновления профиля проверить, что сервис сохраняет отказ до модели при неполном анализе. Не смешивать выигрыш от cache hit с уменьшением стоимости нового текста.

Расчёт мощности: если средняя стоимость полного запроса чата равна `C` CPU-секунд анализа, то грубый CPU-предел — `available_cores × target_utilization / C` запросов/с. `C` включает все реально просканированные блоки, промахи и накладные расходы; это модель, не обещание производительности. Ограничения Redis, сети, памяти, распределения нагрузки и провайдера могут дать меньший предел. Google SRE рекомендует оценивать ресурсы/стоимость запроса, поскольку одинаковый QPS может означать разную нагрузку. [Handling Overload](https://sre.google/sre-book/handling-overload/)

При перегрузке для этой задачи допустим контролируемый отказ, но не частичная проверка. Критерий готовности: улучшение CPU полного профиля на заранее выбранном наборе, отсутствие изменений результатов без отдельного обоснования, отсутствие пропуска текста к mock-провайдеру при отказах, ограниченные очереди и измеренная эффективность масштабирования `throughput_N / (N × throughput_1)` при одинаковом составе запросов.

## Ограничения исследования

Первичная исследовательская часть опиралась на исходники и сохранённый benchmark; выполненные затем локальные эксперименты описаны ниже. Независимые серверные реплики не разворачивались. По локальным процессам нельзя обещать рост мощности сервера в 5–10 раз или отсутствие ложных срабатываний. Не проверены все маршруты upstream LiteLLM и все перехваты исключений вне просмотренного пути. Внешние документы изменяемы; для выпуска нужно закрепить версии зависимостей и проверить установленный runtime. Предложения выше — эксперименты и критерии приёмки, а не заявленные достижения.

## Дополнение: разбор размеченного качества

После основного исследования получен `context-scaling-results.json`. Первый прогон до исправления срока карты показал полное покрытие 381/662 меток ПДн и 389/496 меток секретов; 25/500 отрицательных случаев изменяются. Это покрытие размеченных диапазонов, не готовая метрика precision/recall: состав меток шире стандартных сущностей, а некоторые положительные примеры не проходят валидацию формата. Для следующей классификации прочитаны корпуса и выполнены дополнительные прямые вызовы текущего Detector; исходные значения в отчёт не включаются.

**ПДн: 281 неполная метка.** 224 — банковские бизнес-поля: сумма операции 40, дата/время операции 32, идентификаторы операции/клиента/договора по 24, назначение платежа и баланс по 16, сумма/проценты вклада, остаток/платёж кредита, дата платежа и номер платёжного поручения по 8. Их отсутствие нельзя объяснять дефектом обычного распознавателя имени/документа: для поставленной задачи защиты конфиденциальных данных нужны отдельные контекстные правила банковских полей во внешнем профиле. Ещё 24 метки — банковские счета; 33 — другие ПДн и карточные поля. Это разбиение области ответственности, а не объявление пропущенных бизнес-полей безопасными.

В оставшихся 33 метках есть реальные пробелы и спорные положительные примеры. `LOCAL-SYN-082` (`PAN_19`) не проходит Luhn у `RuBankCardRecognizer`; `LOCAL-SYN-134` (`INN_ORG`) не проходит checksum у `RuInnRecognizer`. Ослаблять валидаторы ради этих меток не следует. `LOCAL-SYN-008` использует camelCase `birthDate`, а правило даты рождения задаётся внешним профилем; это отдельная задача конфигурации, а не автоматически дефект ядра. 13 неполных адресов (7 без покрытия, 6 частичных) и 3 имени без покрытия требуют отдельной оценки границ/контекста.

Небольшое обоснованное улучшение ядра: `LOCAL-SYN-091` содержит явное JSON-поле `card_expiry` со значением формы `YYYY-MM`, месяц корректен. `RuCardExpiryRecognizer` принимает только формы месяц/год. Добавить ограниченный вариант `20xx-(01..12)` после явно карточной метки, сохранив score и строгие границы. Проверить разные годы и месяцы, запрет 00/13, запрет полного `YYYY-MM-DD`, обычные даты и версии без карточной метки. Это расширение общей грамматики явно названного поля. После разбора оно реализовано и проверено: итоговое покрытие ПДн стало 382/662, число ложных срабатываний не изменилось; оставшиеся неполные метки — 280.

**Секреты: 107 неполных меток.** Из 38 частично покрытых 36 размечены как `DATABASE_CREDENTIAL`. В 32 из них метка охватывает URI целиком, а пароль в `scheme://user:password@host` полностью закрыт диапазонами Detector. Это подтверждённое несовпадение гранулярности метки и политики; оно не означает, что все компоненты URI допустимо публиковать при любой политике. Остались 4 частичные DB-метки, 1 access token и 1 password, которым нельзя автоматически присвоить ту же классификацию. У password и одной из DB-меток непокрытым остаётся один знак пунктуации; знак может быть частью секрета, поэтому считать результат полным нельзя. Частичный access token оставляет 177 из 213 символов открытыми — это существенный непокрытый диапазон, требующий отдельного разбора.

Все 69 меток с нулевым покрытием остаются пропусками относительно разметки: password 28, API key 9, access token 8, cloud credential 6, database credential 5, encryption key 5, webhook secret 3, generic secret 3, session secret 2. Среди них 9 значений длиной не более 6 символов; атрибуты корпуса отмечают 3 слабых пароля, 2 примера, 5 test-name и 1 частично маскированное значение. Эти группы могут пересекаться. Атрибут `example` или малая длина сами по себе не доказывают безопасность; blanket-ослабление порогов создаст ложные срабатывания в коде.

**Отрицательный корпус:** повторный вызов Detector подтверждает те же 25 изменённых случаев: `qa_source_reference` 8, `qa_nonperson_ids` 6, `qa_algorithm_constants` 4, `qa_mock_response` 4, `qa_dotted_version` 2, `security_code_identifier` 1. 24 размеченных отрицательных диапазона затронуты, но изменённых случаев 25: в одном случае находка лежит вне отрицательного диапазона. Это причина считать и метки, и изменённые случаи отдельно, а не взаимозаменяемо. Перед снижением порогов распознавания эти категории нужно включить в обязательный контроль.

Это результат продолжения исследования в рабочем дереве после `a1fae8e`, а не новая опубликованная версия. Изменения кода описаны в [RU-MASK.md](../../RU-MASK.md). Оригинальный mask3 wheel и установленный runtime порта не заменялись. Незакоммиченные пользовательские изменения порта сохранены.

Три прохода агрегированы; доверительный интервал не оценивался. Это не обещание такого же ускорения любого чата.

### Локальные процессы

Python 3.13.5, macOS ARM64, 12 логических CPU. Для каждой ступени создаётся новый spawn-pool, каждый процесс загружает профиль. Время запуска отделено от времени конечного пакета. Нет межтекстового кеша сервиса/Redis/LLM; внутренние оптимизации Detector остаются включены. ### Качество и совместимость

- ПДн/банковские поля: 382/662 полностью покрыты (до расширения срока карты — 381), 7 частичных и 273 без покрытия. Это 57.7% полного покрытия меток этого широкого корпуса, не универсальная оценка распознавания российских ПДн.
- Секреты: 389/496 полностью покрыты; 38 частично, 69 без покрытия. Для 32 частичных URI подтверждено полное закрытие password-поддиапазона; политика остальных компонентов URI требует отдельного решения.
- Отрицательные сообщения: 25/500 затронуты; 24/500 явно безопасных диапазонов затронуты. Новое правило не добавило ложных срабатываний на этом наборе.
- 2072 теста ядра и 7 subtests прошли. 134 теста с недоступной английской моделью или pytest-mock исключены; это не полный upstream suite. Первоначальные ошибки загрузки отсутствующей модели не считались дефектами оптимизации. Десять старых ошибок ожиданий конфигурации исправлены.
- 66 тестов соседнего порта прошли: protocol, batch, streaming, локальный/shared/Redis cache и admission. Они используют тестовые HTTP endpoints/подмены и не доказывают все маршруты production-LiteLLM. Файлы и ограничения запуска перечислены в [validation-results.json](validation-results.json).

### Уточнённые причины трёх неполных секретов

Дополнительное исследование установило: частичный ACCESS_TOKEN имеет JWT-подобную форму с длинами сегментов 36/168/7 и заголовком HS256. Правило профиля требует подпись не короче 10 символов, а явно подписанный JWT не включает общую метку `token`. Встроенный `other-token` захватывает только первый сегмент. Это вопрос политики для повреждённых/примерных токенов; по одному примеру ослаблять проверку формата нельзя.

Два других случая — подтверждённый дефект границ `generic-api-key` в `presidio_analyzer/conf/gitleaks-source.toml`: завершающий `?` пароля не входит в класс символов и остаётся вне маски, в том числе внутри кавычек. Синтетический пример `{"db_password":"Abcd%Efgh!J?"}` воспроизводит усечение в ядре и полном профиле. Это остающийся дефект, не исправленный описанной оптимизацией. Следующая правка должна отдельно разбирать явно закрытые кавычками значения, проверять их полную длину и не включать вопросительный знак предложения в некавыченный секрет. Нужны контрольные примеры escaped quotes, одиночных/двойных кавычек, незакрытой строки, `?` внутри значения и source-code references; менять общий класс символов без такого разделения небезопасно для ложных срабатываний.
