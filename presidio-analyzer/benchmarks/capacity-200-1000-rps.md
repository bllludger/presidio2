# Новое ядро: 200 и 1000 запросов чата в секунду

Дата: 24.11.2026. Пользователь уточнил: RPS означает запросы чата; серверное железо пока не выбрано. Правила, runtime-код и конфигурация работающих сервисов в этом исследовании не менялись.

## Вывод

200 и 1000 chat RPS не являются фиксированными возможностями версии ядра. Для измеренного небольшого чата цель 200 выглядит достижимой при достаточных ресурсах; 1000 теоретически достижима горизонтальным масштабированием. Гарантии для текущего порта нет: 1000 полных chat RPS не испытаны, а тяжёлые новые блоки требуют на порядок больше CPU. При шаблонных настройках 4 workers / 4 in-flight обещать эти цели нельзя.

Считать нужно стоимость полного Detector с фиксированным профилем. «Пустое ядро без правил» не даёт полезной оценки мощности. Правила при этом не меняются: меняются входной текст, cache misses, ресурсы и организация обработки.

## Новые измерения

Среда: Apple M3 Pro, 6 performance + 6 efficiency cores (sysctl), macOS ARM64, Python 3.13.5. Это не 12 одинаковых серверных ядер. Загружены исходники нового `presidio-ru-core` и оптимизированный профиль порта. Файлы JSON фиксируют используемый runtime и corpus hashes. Нельзя переносить число локальных workers прямо в число серверных vCPU.

### Стоимость одного чата

Использована существующая функция `litellm-presidio-port/tests/openrouter_history.py:messages_for`: четыре сообщения с Python-кодом и одно короткое сообщение; суммарно около 17,4 KB. Адреса синтетические, уникальные для свежих историй. Detector прогрет. Три серии по 100 чатов; для всех 3000 проверенных блоков двух сценариев проверена одна ожидаемая находка.

| Сценарий | CPU mean на чат | CPU p95 на чат |
| --- | ---: | ---: |
| Все 5 блоков требуют анализа | 15.737 ms | 16.360 ms |
| 4 блока истории в локальном кеше + 1 новый короткий | 0.367 ms | 0.393 ms |

Источник: [capacity-chat-cost.json](capacity-chat-cost.json). Это CPU прямого Detector / worker-local cache. Здесь нет HTTP, LiteLLM, shared/Redis lookup, подготовки запроса, маскирования, карты восстановления и провайдера. 0,37 ms нельзя выдавать за стоимость полного cache-hit чата. Новые истории обходили межтекстовый сервисный кеш, но сохраняли штатные внутренние оптимизации Detector. Код повторяющийся: это контролируемый сценарий, не production-распределение входов.

### Масштабирование тяжёлого корпуса

Повторно запущен существующий `evaluate_ru_port.py --workload server --workers 1 4 8 12 --repeats 2`. 256 входов, поровну 8/32 KB, два прохода на ступень; все диапазоны работников совпали с последовательным результатом. Это конечный пакет, а не поступление чатов с заданным RPS.

| Workers | Блоков/s | CPU ms/block | p95 сканирования | Эффективность относительно 1 worker |
| --- | ---: | ---: | ---: | ---: |
| 1 | 16.3 | 61.11 | 114.5 ms | 100.0% |
| 4 | 58.9 | 66.85 | 129.1 ms | 90.3% |
| 8 | 104.5 | 75.25 | 144.1 ms | 80.1% |
| 12 | 89.6 | 94.11 | 299.9 ms | 45.8% |

Источник: [capacity-current-server.json](capacity-current-server.json). 12 workers хуже 8 в этом опыте. Причины по отдельности не измерялись; нельзя объявлять результат доказательством конкретного эффекта GIL, планировщика или памяти. Он прямо показывает, что линейное масштабирование на одной машине не обеспечено. При пяти таких блоках на чат деление 104,5 на 5 даёт лишь условные 20,9 chat/s обработки блоков, без остальных частей тракта; это не измеренный end-to-end RPS.

## Ресурсная модель

Для частоты `R` chat/s и `C` CPU-ms анализа на чат:

```text
busy CPU equivalents = R × C / 1000
scan capacity at target utilization u = ceil(R × C / (1000 × u))
C = sum(cost of fresh/missed blocks) + sum(cost of cache hits)
```

В таблице выбран `u = 0.70` как плановый запас, не доказанная граница p99. Это эквиваленты измеренной CPU-производительности только под анализ. Они не являются готовой спецификацией покупки серверов. Нужны калибровка на выбранном CPU, поправка на падение эффективности под конкуренцией и отдельный бюджет на HTTP/прокси/Redis, резервирование и пики.

| Сценарий на один чат | CPU ms/chat | CPU для 200 chat/s при 70% | CPU для 1000 chat/s при 70% |
| --- | ---: | ---: | ---: |
| 5 новых блоков кода, ~17 KB суммарно | 15.74 | 5 | 23 |
| 1 новый серверный блок 8 KB | 22.34 | 7 | 32 |
| 1 новый серверный блок 32 KB | 97.66 | 28 | 140 |
| 5 новых серверных блоков по 8 KB | 111.68 | 32 | 160 |
| 5 новых серверных блоков по 32 KB | 488.32 | 140 | 698 |

[Проверяемые расчёты](capacity-model.json). Стоимость отдельных 8/32 KB взята из последнего [попарного замера нового ядра и оптимизированного порта](../../../litellm-presidio-port/runs/profile-cpu/local-core-comparison.json), а не из старого mask2. Варианты с пятью такими блоками — линейные сценарии стоимости, не отдельно проведённый нагрузочный тест этих чатов.

Кеш важен по стоимости, а не только по числу попаданий: четыре дешёвых hit и один большой miss могут оставаться дорогими. Для защитимого sizing нужен взвешенный по CPU/размеру hit rate, отдельно cold cache и сценарий недоступного Redis. В таблице эффект кеша намеренно не используется как гарантированная скидка.

## Ограничения порта

Подробный независимый просмотр: [capacity-port-audit.md](capacity-port-audit.md). Шаблон `config/litellm.yaml` задаёт 4 in-flight, 32 ожидающих, 2s очереди и 5s HTTP; analyzer по умолчанию запускает 4 процесса. Максимум 32 workers одного анализатора и 32 in-flight одного guardrail не ограничивают суммарное число реплик, но требуют настроить распределение нагрузки, а не просто увеличить целевой RPS клиента.

Для 200 chat/s ×5 проверок получается 1000 block/s; четырём слотам нужен средний полный HTTP-slot менее 4 ms даже без запаса. Для 1000 chat/s ×5 — 5000 block/s и менее 0,8 ms. Поэтому CPU-оценка одного сканирования не доказывает достаточности текущего admission/HTTP-тракта. Увеличение очереди не добавляет CPU, а лишь меняет ожидание и отказы.

Исторические 200 RPS относятся к блокам, старому mask2 и десятисекундному смешанному тесту; их нельзя выдавать за новый результат 200 chat/s. Скрипт `queue_scaling.py` жёстко извлекает mask2 wheel, поэтому его неизменённый запуск не проверяет нынешние исходники.

## Что ещё требуется от ядра по ресурсной устойчивости

`strict_scan()` в `presidio_analyzer/scan_policy.py` запрещает выдавать частичный результат после таймаута, но не задаёт общий временной/CPU-бюджет на блок. `PatternRecognizer` и IBAN по умолчанию используют `REGEX_TIMEOUT_SECONDS=60`. HTTP timeout порта 5s не прерывает синхронный `Detector.detect()` в серверном процессе: клиент может перестать ждать, пока worker продолжает работу. Это вывод из пути вызовов, не результат нового adversarial-теста.

Перед обещанием устойчивых 200/1000 RPS нужен согласованный бюджет анализа: оставшееся время до общего deadline для regex, проверки бюджета между компонентами, контролируемый отказ без частичного результата и стратегия прекращения оставшейся работы после отмены. Для компонентов без прерывания нужна проверенная граница размера/времени либо изоляция исполнения. Это задача выполнения и ресурсов, а не изменение правил распознавания. Нельзя просто снизить таймаут и объявить нагрузку выдержанной: потерянные/отклонённые чаты не считаются успешным RPS.

## Приёмка перед обещанием мощности

1. Выбрать серверный CPU и лимиты контейнеров; закрепить собранный wheel, профиль, размеры/число блоков, p95/p99 latency SLO и допустимую долю отказов.
2. Измерить CPU полного чата и память всех workers на новом тексте, повторных историях, смешанном потоке и неблагоприятных длинных входах.
3. Провести open-loop прогон реального LiteLLM с локальной mock-моделью на 200 и 1000 именно chat/s; фиксировать offered/успехи/ошибки/отказы, client scheduling lag, очередь, CPU/RSS, correctness маскирования и восстановления. Длительность и число повторов должны позволять увидеть накопление очереди; короткий burst не заменяет устойчивую нагрузку.
4. Проверить cold cache, Redis failure, отмены, смерть worker и rolling restart без отправки непроверенного текста модели.
5. Повторить с настоящим backend отдельно: доступность/лимиты модели и скорость streaming не являются свойствами ядра.

Итог: для синтетического нового чата ~17 KB модель даёт около 5/23 эквивалентов CPU только под анализ на 200/1000 chat/s при 70%. Это полезная стартовая оценка, не гарантия. Для больших новых историй потребность растёт до десятков/сотен ядер. На текущем дефолтном запуске и без выбранного железа обещание «выдержит всё» не подтверждается.
