# Аудит ограничений порта для оценки 200/1000 RPS

Дата: 2026-11-24. Статический аудит локального кода и исторических результатов; новые нагрузочные тесты здесь не выполнялись. Изменён только этот новый файл.

## Что ограничивает текущий порт

- `litellm-presidio-port/config/litellm.yaml:17–20`: 4 одновременных вызова анализатора, 32 ожидающих, ожидание до 2 с, HTTP до 5 с.
- `src/presidio_ru_litellm/guardrail.py:424–440`: те же значения по умолчанию; максимум 32 in-flight, до 1024 waiters. Ограничение действует на экземпляр и event loop (`:444–449`), поэтому процессы прокси складывают нагрузку на общий анализатор.
- `src/presidio_ru_litellm/analyzer.py:175–178`: по умолчанию 4 процесса, допустимо 1–32. Каждый процесс обслуживает синхронный HTTPServer; batch выполняет элементы последовательно (`:100–103`). Backlog128 (`:50–51`) не является вычислительной мощностью.
- При четырёх слотах необходимое условие для 200 блоков/с — среднее время занятости слота менее 20 мс, для 1000 — менее 4 мс; для приемлемой очереди нужен дополнительный запас. Это условие через закон сохранения потока, не результат измерения. Четыре слота не означают жёсткий лимит4RPS и сами по себе не доказывают невозможность200.
- Увеличение очереди сглаживает всплески, но не повышает устойчивую пропускную способность. `guardrail.py:370–393` отклоняет переполнение и истёкшее ожидание.
- Входной лимит LiteLLM удерживает весь HTTP-запрос, включая модель и streaming (локальный README:60). В шаблоне `config/litellm.yaml` он явно не задан; нельзя выдавать лимиты из экспериментальных конфигураций за default. Для R chat/s и среднего времени T секунд нужно как минимум R×T одновременно обрабатываемых чатов, отдельно от слотов сканирования.

## Что действительно проверял queue_scaling.py

`benchmarks/queue_scaling.py:270–275` извлекает wheel `*ru.mask2*.whl`, а не текущий код `presidio-ru-core`. Запуск скрипта без изменения подключения ядра не подтверждает масштабирование нового ядра.

`queue_scaling.py:87–110`: каждый блок уникален благодаря новому email; длинный блок — повторённый240раз фрагмент Python (~17,5тыс.символов), короткий — контакт. В steady80%коротких и20%длинных (`:169–175`). Проверяется один `analyze_text`, не полный chat, не вызов модели и не анонимизация. Историческая фаза200 длится примерно10с (`:187–189`).

CPU измеряется `process_time_ns` вокруг `CachedTextDetector.scan` (`:34–42`): включает lookup кеша и детекцию, исключает ожидание очереди, HTTP parsing/serialization, прокси и модель. ## Почему блоки не равны чатам

Чат может содержать много сообщений, tool results и мультимодальных текстовых частей. При B проверяемых блоках на чат грубая нагрузка равна R_chat×B, а при hit fraction h новое сканирование приблизительно R_chat×B×(1−h). Даже кешированные блоки требуют hashing, обращения, сериализации и прохода по истории; нулевую стоимость им приписывать нельзя. Локальный кеш1024 и shared4096 хранят только результаты до32 spans (`analyzer.py:25–46`, README:38); высококардинальные новые тексты не получают выгоду от повторов.

## Вывод для оценки нового ядра

200 и1000 RPS требуют определения единицы нагрузки, распределения длин, числа новых блоков, cache hit rate, доли секретов/ПДн, допустимых p95/p99 и отказов. Теоретический CPU-бюджет считают по среднему CPU времени нового сканирования: cores≈R_block×CPU_seconds/utilization_target, добавляя стоимость HTTP/прокси/кеша. Логический CPU, процесс worker и полноценное серверное ядро не взаимозаменяемые единицы; измерение на клиентском компьютере не даёт автоматического коэффициента для серверных vCPU.

Текущие результаты допускают200блоков/с для узкого старого синтетического сценария с6процессами, но не доказывают200чатов/с и тем более1000. Новое более быстрое ядро может сделать эти цели достижимыми после корректного подбора процессов, слотов, числа реплик и входной ёмкости; требуется open-loop проверка именно нового ядра через полный целевой тракт, с уникальными текстами и репрезентативными историями, учётом всех offered/ok/rejected, CPU, памяти и хвостов задержки.
